# Contributing to CodeBoard

## Setup

```bash
npm run examples  # the repository the tests run on, examples/nano-vllm (under a second; in a git worktree it comes from the main checkout, nothing fetched); sglang and DeepEP are only for trying things by hand: npm run examples -- sglang DeepEP
npm install
npm run build      # the extension after the workspaces it depends on (tools/build.mjs): @yhnocoder/markdown (packages/markdown/dist), box (packages/box/bin, with cargo), the board UI (packages/board/dist, which the extension build copies into its media/board) and the extension (extensions/vscode/dist; no .vsix)
npm test           # unit tests (analysis, core, box, markdown, board, host, extension); the box and host ones need the box build
npm run check      # local test tier: typecheck, lint, unit tests and affected harness scenarios (~90 s)
npm run lint       # Biome (formatting at 120 columns, no unused imports, no `any`; biome.jsonc) and knip (dead code: any finding fails); part of check and CI
npm run format     # format every file with Biome
npm run e2e        # main flows in a real VS Code, with screenshots (needs VS Code and xvfb)
npm run storybook  # Storybook for the board UI at http://localhost:6006 (cards and toolbar, every theme, light / dark, zoom); not part of check or the per-push CI. `npm run storybook:check` builds it and opens every story in Chromium; that runs in the regular full test run, every 6 hours (`.github/workflows/regular.yml`)
```

`npm run mac` builds the macOS app (`apps/macos/build.sh`: the JavaScript side bundled for JavaScriptCore with esbuild, `swift build -c release`, `apps/macos/build/CodeBoard.app` signed ad hoc with the hardened runtime; needs Xcode 26 or later); `npm run mac:run -- --open ~/Projects/persona` builds and opens a project. `apps/macos/Sources/CodeBoard/main.swift` lists the launch arguments the checks use (`--auto` for the scripted run with frame timings, `--snapshot <dir>` for PNGs of the canvas without screen capture). Its JavaScript side has vitest tests (`npm test -w @codeboard/macos`), the Swift side `swift test` in `apps/macos`.

`npm run package` builds everything and packs an installable `.vsix` into `extensions/vscode/`. Releases do the same in CI (`.github/workflows/release.yml`), with box built for linux-x64 and linux-arm64 (static, musl), darwin-arm64 and darwin-x64 (macOS 15 and later, set in `packages/box/.cargo/config.toml`), win32-x64 and win32-arm64 first and all six bundled in the one `.vsix` (`bin/<platform>-<arch>/`). To release:

1. Bump `version` in `extensions/vscode/package.json` in a PR and merge it (add a `CHANGELOG.md` entry in the same PR).
2. Push the tag `v<that version>`; a tag that does not match fails the release. CI builds the `.vsix` and screenshots into a draft GitHub Release.
3. Review the draft (install its `.vsix`), then **Publish release**. That publishes exactly that `.vsix` to the VS Code Marketplace and Open VSX (the `publish` job, in the `marketplace` environment). To publish an already published release again, run the Release workflow by hand with `publish_tag` set to its tag.

One-time setup for the stores: create the Marketplace publisher `yhnocoder`; add an Azure DevOps personal access token (Organization: All accessible organizations, scope Marketplace: Manage) as the repository secret `VSCE_PAT`; create an Open VSX access token, add it as `OVSX_PAT`, and create the namespace once with `npx ovsx create-namespace yhnocoder -p <token>`. Until a secret is set, its store is skipped with a notice. Add required reviewers to the `marketplace` environment to approve each publish.

### Releasing @yhnocoder/markdown

`packages/markdown` is published to npm as `@yhnocoder/markdown` by `.github/workflows/markdown-release.yml`, with npm Trusted Publishing (no token; the package gets a provenance statement). Bump `version` in `packages/markdown/package.json` in a PR (with its entry in `packages/markdown/CHANGELOG.md`, which is published with the package) and merge it, then push the tag `markdown-v<that version>`: the workflow checks the tag against the version, builds, runs the package's unit tests and the demo, and stages the version on npm (`npm stage publish`; the Trusted Publisher allows only staging). The owner then approves it with 2FA on npmjs.com, or with `npm stage list @yhnocoder/markdown` and `npm stage approve <stage-id>`, and only then is it published. The very first version was published by hand once (`npm publish -w @yhnocoder/markdown --provenance=false` from a clean checkout of main after `npm ci`, signed in to npm as the package owner; provenance needs CI), so that the package exists and `markdown-release.yml` can be added as its Trusted Publisher on npmjs.com (package settings, GitHub Actions, repository `yhnocoder/codeboard`).

To debug the extension, open this repository in VS Code and press `F5`: **CodeBoard：在 persona 上调试插件** (the default) opens `~/Projects/persona` in a new window with the extension installed, **CodeBoard：在 nano-vllm 上调试插件** `examples/nano-vllm`. From a terminal, `npm run try [-- <folder>]` does the same without opening this repository first: it builds the current checkout and opens the folder (default `~/Projects/persona`) in an Extension Development Host.

On macOS the tests run too (CI runs only Linux): install the browser once with `npx playwright-core install chromium` (used when `/opt/pw-browsers/chromium` is not there); `npm run e2e` opens a real window of `/Applications/Visual Studio Code.app` (no xvfb). Scenarios and e2e steps write shortcuts as `ControlOrMeta+…` and caret keys the PC way (`Home`, `Control+End`); on a Mac `tools/test/mac-keys.mjs` turns those into ⌘← / ⌘↓ and the like.

A script that needs a browser launches it with `launch()` from `tools/test/chromium.mjs` (the repo's `playwright-core` with the browser CI or the cloud image provides), not with a bare `require("playwright")`, whose pinned browser revision the cloud image may not have.

Test tiers, time budgets and how scenarios are selected are described in [TESTING.md](TESTING.md).

## Repository layout

- `packages/analysis`: code analysis with tree-sitter (symbols, calls, loops, comment / docstring lines, selections, cross-language boundaries), the language table (`langs.ts`) and the few types and helpers that analysis results and the board model share (`basics.ts`; the board imports `@codeboard/analysis/langs` and `/basics`, never the tree-sitter entry). The tree-sitter wasm are its dependencies: the runtime, Python and Rust from `@vscode/tree-sitter-wasm`, C / C++ / CUDA from `@yhnocoder/tree-sitter-cuda` (our tree-sitter-cuda fork, installed from its GitHub release tarball). It imports no other CodeBoard package: core depends on it. To see how well the analysis does on another repository: `npm run stats:analysis -w @codeboard/analysis -- <repo dir> [--lang cuda,cpp,python] [--json out.json]` (per language: parse errors, symbols, calls, kernel launches, analyze / parse time, pybind and TORCH_LIBRARY bridges); `npm run bench:analysis -w @codeboard/analysis -- <dir>` times the Python analysis against the old one
- `packages/core`: data model, syncing cards with the current code (pure TypeScript, with tests). Besides the main entry: `@codeboard/core/canvas` (the canvas geometry: curves, arrow routing, label placement, hand-drawn strokes), `@codeboard/core/history` (the undo engine and saving: snapshots, undo / redo, syncs replayed after undo, per-board histories, the patches sent to the host), `@codeboard/core/commands` (the board's command layer: what a board button, menu item or key does to the board, by area: `cards.ts`, `code.ts`, `notes.ts`, `links.ts`, `calls.ts`, `sections.ts`, `stickers.ts`, `shared.ts`, `variants.ts`, `versions.ts`, `web.ts`, `subboards.ts`; they reach the store, the host, dialogs and toasts only through a `CommandEnv`, which the board wires in `packages/board/src/actions/env.ts`), `/settings` and `/tidy`. Logic another shell needs without a DOM or Solid goes here, so a native app can run it on board JSON
- `packages/markdown`: the Markdown renderer and editor on their own (schema, static render and `hydrate`, the TipTap editor, the CodeMirror code editor and their stylesheet), configured through an instance (`createMarkdown(options)`: resolvers, highlighter, math preamble, image addresses and the caches built under them; the board makes one in `wireBoard` and hands it to its components through `MdContext`), never through module-level setters. Entries: `@yhnocoder/markdown` (read-only: `createMarkdown`, the schema, layout and selection helpers; no Solid), `/editor` (the editor, `mountEditor(md, …)`, loaded lazily), `/code-editor` (CodeMirror on its own, as in Free code cards), `/ui` (the shared key forwarding (`keepKey(e, passKeys)`), popover placement, in-box scrolling (`scrollIntoBox`), a page's measure batching (`createMeasure`) and its hold on AI completions (`createGhostHold`) the board shares with its instance, pausing them while it moves or resizes a card), `/style.css` and `/katex.css`. It is published to npm, and its build (`npm run build -w @yhnocoder/markdown`: `dist/` with the Solid JSX compiled, `.d.ts` declarations and the two stylesheets) is what the board and the demo use too, exactly as an npm user would; `solid-js` is a peer dependency. The root `npm run build` builds it first, and `npm run check` before anything else; after changing `packages/markdown/src`, rebuild it before typechecking or building the board on their own. Its README is the npm page
- `packages/box`: box, the local knowledge index behind ⌘K's Related by Meaning, in Rust (needs a Rust toolchain: https://rustup.rs; without cargo the build says so, Related by Meaning is off and its tests skip). A cargo workspace: the index itself is `core/` (`box-core`, `Index` in `index.rs`): items cut into the whole text plus each paragraph, and their images each embedded on its own (`chunk.rs`), embedded by an OpenAI-compatible endpoint the user runs with EmbeddingGemma's prompts (`embed.rs`), content kept once by hash and per-source manifests (CodeBoard: the storage folder at its git branch) in SQLite in the user's data folder (`store.rs`), searched by brute force over int8 vectors with EmbeddingGemma's large dimensions clipped (`vectors.rs`), through an HNSW graph (usearch) from 200 000 vectors on (`graph.rs`), and by keyword in a tantivy index of its own (`keyword.rs`, the `search_keyword` request); a search's best text hits are read again by the embedding server's reranking model (`rerank.rs`, the `rerank` request: `POST {base}/rerank`). CodeBoard uses it through the service, one per user (`box serve`, `src/service.rs`, started by the first client that needs it and gone after 10 idle minutes) on a local socket with a token file, shared by every VS Code window; single-process apps embed it instead: the Node addon (`node/`, napi-rs) and the C ABI (`ffi/`) with the Swift package over it (`swift/`); `README.md` there has how. The requests are in `PROTOCOL.md`. The same folder is the npm workspace `@codeboard/box`: the TypeScript client (`src/index.ts`, `connect()`) and `build.mjs` (`npm run build -w @codeboard/box`: `cargo build --release`, the binary copied to `bin/<platform>-<arch>/`, where the host's tests and the extension's build take it, and the addon to `node/bin/<platform>-<arch>/box.node`; a release builds every platform's with `box.yml`, which builds each on its own runner and smoke-tests it there: cargo's tests, the binary through the client (`test/smoke.mjs`), the addon (`test/smoke-addon.mjs`) and on macOS `swift test`; a PR that changes `packages/box` runs it too, on Linux only; Windows and macOS are built and tested only for a release). `cargo test` and `cargo clippy --workspace --all-targets -- -D warnings` in `packages/box` run in `npm run check` (tests) and CI (both). The host's `meaning.ts` hands it the project's cards and sidenotes (source: the storage folder, ref: its git branch, groups: the boards each is on), with the pictures of Image cards and Notes as data: URLs read from `assets/` (an SVG is drawn into a PNG by an open board, `HostToBoard` `draw`, and its `<text>` indexed as the card's text; box never reads files); the binary reaches the host as `HostOptions.box`
- `packages/board`: the board UI (SolidJS), bundled into the extension's webview
- `packages/host`: the editor-independent host: reads code, highlights it (shiki, and tree-sitter through the analysis; `src/highlight.ts`), resolves calls, tracks versions, stores and coordinates boards. Two entries: `@codeboard/host` (`src/index.ts`: `startHost`, which wires a whole host from a `Workspace` and a `HostEnv`, and the few pieces an editor shell draws itself) and `@codeboard/host/testing` (`test/testing.ts`: what the board's scenarios, harness and stories use directly, with the Node `Workspace` and the generated test images)
- `apps/macos`: the macOS app: AppKit and Core Animation around `@codeboard/core` and the host's storage running in JavaScriptCore (`js/`: the bridge, `Sources/CodeBoard`: the app)
- `extensions/vscode`: the VS Code extension: the VS Code adapters around `packages/host` (activation, webview panels, sidebar, CodeLens, commands, the `Workspace` implementation)
- `examples/`: test repositories as git submodules (nano-vllm, sglang, DeepEP)
- `examples/markdown-demo`: a small Vite page that uses only `@yhnocoder/markdown` (static render, click to edit, save, light / dark); its Playwright test (`npm test -w @codeboard/markdown-demo`) runs in `npm run check` and CI
- `explore/`: requirement explorations and prototypes
- `tools/`: test runner, release and review scripts

## Architecture rules

Rules to keep when changing code (from the v0.1 and v0.1.5 architecture reviews):

- **Every board change goes through the store.** User edits use `mutate()` (recorded for undo), which the board reaches only as `CommandEnv.edit`, through the commands. Changes synced from the host or derived by the view use `sync()` (saved, not recorded for undo, replayed after undo). Both come from `packages/board/src/state/changes.ts`, which wires core's undo engine and saving (`@codeboard/core/history`: `history.ts`, with `snap.ts` and `upkeep.ts`, and `save.ts`) to the Solid store; the engine reaches the board only through its `Doc`, `Hooks` and `HistoryPorts` (how a Note splits into blocks), and its tests run on a plain object (`packages/core/test/history.test.ts`). Core imports no UI framework (`packages/host/test/boundary.test.ts`). Segment views and version states (`state.views`, `state.stale`) are written only through `state/views.ts`; only these two files import the store's `setState`, the rest of the state has its own setters in `store.ts`. A board unit test (`test/unit/state-shape.test.ts`) checks this by shape. The engine snapshots only the items an edit wrote to (`history/track.ts`: the board a change gets is a proxy that marks the card, place entry, link, Section, Sidenote or sticker each write lands under), so inside a change an object lives under one item: copy what goes under a second one (`clone`), don't share it, and clone what you read through the board only after `raw` (as on the Solid store, `structuredClone` can't take the proxy). The self-check warns `snapshot missed a change` when a snapshot differs from a whole one; the harness fails on it.
- **The board's module-level state is the current board's and resets itself on a board switch.** Declare it with the helpers in `packages/board/src/state/root.ts`: `boardSignal`, `boardStore`, `boardMap`, `boardSet`, `boardRef` and `boardTimer` (a store of what mounted cards measured passes `keep`, so a card that stays mounted across the switch keeps its entry). What outlives a board (the camera, the clipboard, caches by content, id counters, entries owned by mounted components) is listed with its reason in `packages/board/test/unit/state-shape.test.ts`, which checks this by shape. Components pass what they create (a layer registry, a size watcher, a memo) to whoever needs it as a value, never through module variables.
- **The board is started and wired explicitly.** A shell boots it with `boot(transport, options)` (`packages/board/src/boot.tsx`, built as `boot.js`): the VS Code webview's entry `index.tsx` (`board.js`) passes a transport over `acquireVsCodeApi()`, the harness's pages and the stories their own; the board reads no globals of its shell. `wireBoard` (`src/wire.ts`) connects the transport and wires the board's effects and registrations in order; no module starts anything when imported (`test/unit/state-shape.test.ts`).
- **Reference upkeep lives only in `packages/core/src/edit/`** (`refs.ts`: removing and renaming cards, links, sidenotes and stickers; `lines.ts`: following a segment's lines; `ops.ts`, `twins.ts`, `merge.ts`, `notes.ts`: the board actions' structural changes; `blocks.ts`: arrow ends on a Note's blocks; `check.ts`: `danglingRefs`). Delete cards with `removeCards`, links with `removeLinks`, sections / sidenotes / stickers with `removeSections` / `removeSidenotes` / `removeStickers`, change a segment with `rebaseSegment`, swap cards (merge, split, split a Compare) with `replaceCards` / `retargetCards`, and reorder with `arrangeCards`; Compare, inserting a card into an arrow, sidenote ↔ card and Turn into Board each have one op too (`makeCompare`, `splitLink` / `joinLinks`, `sidenoteToCard` / `cardIntoSidenote`, `cardsToFrame`). No other file in core, the board or the extension replaces, filters, reorders or deletes in place from a board's collections (cards, links, sections, sidenotes, stickers, place); they only push new items and change fields of single objects. The only exceptions are `edit/`, `migrate.ts` and `patch.ts` (the storage transport), and a core test guards this by shape. In dev builds, unit tests and the harness (whose pages boot the board with `selfCheck: true`) every user edit ends with a `danglingRefs` self-check (Variant structure included; `HistoryPorts.selfCheck`), and any hit in the harness counts as a failure; production builds skip it, since it walks the whole board on every edit.
- **Host code lives in `packages/host` and reaches the editor only through `Workspace` and `HostEnv`.** Host code gets a `HostContext` (`packages/host/src/context.ts`), made by `startHost` and passed explicitly, and calls its `ws` (the `Workspace` interface is in `packages/core/src/workspace.ts`) to read and find files, ask for definitions, read and write settings and per-workspace state, open editors and show messages. Everything a host remembers (caches, indexes, background work, its log, the syntax trees kept per file for incremental parsing) belongs to its `HostContext`, never to a module, so two hosts can run in one process and `dispose()` lets go of all of it; a feature keeps its state in a class of its own module (`DefCache`, `CodeEdit`, `SettingWrites`…) and the context holds one of each, without knowing what is inside; only the parsers and the content-addressed analysis and highlighting caches are per process; the board coordination (`packages/host/src/hub.ts`) also gets cross-workspace state and new board views from `HostEnv` (`packages/host/src/env.ts`). It never imports `vscode`. The host's wiring (storage, board coordination, analysis, the name index, version checks and the events between them) lives in `startHost` (`packages/host/src/start.ts`), so another shell is just another caller of it. `extensions/vscode` holds only the VS Code adapters: the `Workspace` implementation (`src/vscode/`), the webview panels and `HostEnv` (`panel.ts`), activation, the sidebar, CodeLens and command registration (`extension.ts`, `sidebar.ts`, `lens.ts`, `commands.ts`), and imports the host only from `@codeboard/host`. Its `package.json` `contributes.commands` and `contributes.configuration` are generated by `npm run build` (`src/contributes.ts`) from the host's command table (`packages/host/src/commands.ts`, which `makeActions` must match) and core's settings declarations (`packages/core/src/settings.ts`, also what the host validates board edits against): edit those, not `package.json`. A local build (and `npm run check`, before the unit tests) writes them into `package.json`; in CI the build only compares and fails when the committed `package.json` differs (`node esbuild.mjs --check` does the same locally), and `test/package.test.ts` fails on any difference too. Tests, the harness and stories import the host only from `@codeboard/host` or `@codeboard/host/testing`; the board's own code not at all. Nothing in `packages/` imports from `extensions/`. `packages/host/test/boundary.test.ts` checks this.
- **Boards, shared cards and assets are read and written through `Storage`** (`packages/host/src/storage/`, on the `Fs` port: `boards.ts` the board files and their cache, `library.ts` the shared-card library, `merge.ts` the three-way merges with what other windows wrote, `queue.ts` the write queue, `trash.ts` `.trash/`, `place.ts` which folder the boards are in). The listing is kept while the storage folder and its group folders keep the mtimes they had when it was read (one stat each, however the change was made), so listing and loading boards do not read the folder again; the watcher only merges what another window wrote into open boards and shared cards; core keeps only the pure parts (`patch.ts`: `mergeFile`, `deflate`, `inflate`). The rest of the host's I/O (git, the source files, caches) may use Node directly.
- **The only compat code is old-file upgrade.** `packages/core/src/migrate.ts` brings v1–v11 files to the current format, v12 (`BOARD_VERSION` in `model.ts`: fills defaults, drops false-only flags, rewrites the old editor's `\$…\$` formulas into `$…$`, drops Text cards' fixed heights, writes `[[refs]]` with their target's id, makes the old Free Text H1; the camera a pre-v9 file carried, and the dropping of shared Text cards' heights (their look is in the card library), reach Storage only through `readBoardFile`); after that the schema is strict, and nothing else writes `?? oldValue`, old field aliases or dual paths.
- **Use libraries for mature general problems** (diff, Markdown, popover positioning, SVG sanitizing, file validation). Write the board's own interactions (canvas, arrows, call tree) ourselves, and don't force a library where heavy customization would be needed.
- **No compatibility code outside migration.** Old board files are upgraded to the current format in one migration step; there are no shims, fallbacks, legacy aliases or dual code paths elsewhere. Fix root causes and replace old behavior outright.
- **Every UI operation runs at 60 fps.**
- **Board actions are UI glue; the rules are commands in `@codeboard/core/commands`.** What a change does to the board (which items go, where references move, what a merge, split, Compare, Section, Variant, version update, sidenote ↔ card or Turn into Board makes, what the user is asked first) is a command, so another shell gets the same behaviour from it; `packages/board/src/actions/*` keeps only what is about this UI: selection, popovers, menus, animation, measuring and placing on screen (passed to a command as a value or a callback), toasts and views. Every user edit is a command, a plain field change too (a title, a lock, a colour, a wrap toggle: one named command per field, taking the value, never a function from its caller). The board never imports core's structural edits (the functions in `core/src/edit/` that change a board, and the variant and sub-board ones) from `@codeboard/core`; only commands call them, and a change the host already made that the board applies as a sync uses a core op for it too (`dropGone`). Outside `state/changes.ts`, which defines it, the only `mutate()` in `packages/board/src` is the command env's `edit` (`actions/env.ts`). `packages/board/test/unit/commands-shape.test.ts` checks both by shape. A new card or question with nothing written yet goes through `CommandEnv.fresh`, so the rule that one left empty disappears is a command too.
- **Every board gesture goes through `packages/board/src/gesture.ts`.** A pointer drag uses `track()` (and `undoGesture()` for its undo step), a gesture that is not a drag `holdGesture()`, the pointer followed with no button held (placing a sticker) `followPointer()`: a board switch halfway drops it, so nothing of the old board is committed or reaches the new board's undo stack. Don't add window pointer listeners of your own for a drag; `test/unit/state-shape.test.ts` checks both by shape.
- **No circular imports.** `packages/host/test/cycles.test.ts` fails on any cycle inside a package (runtime imports; `import type` and lazy `import()` don't count). When two modules need each other, move what they share into a third module both import, or the code into the layer it belongs to; don't break a cycle with a lazy `import()`, a type-only trick or a setter that injects a function at load time.

## Pull requests

- Name tests by what they test, never by version.
- For small changes, run locally only the unit tests and the tests related to what you changed (`npm run check` does this); CI runs the rest. Run the full suite locally for big or risky changes.
- Keep the README user-facing. Development notes belong here or in [TESTING.md](TESTING.md).
