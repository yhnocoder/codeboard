# Contributing to CodeBoard

## Setup

```bash
npm run examples  # the repository the tests run on, examples/nano-vllm (under a second; in a git worktree it comes from the main checkout, nothing fetched); sglang and DeepEP are only for trying things by hand: npm run examples -- sglang DeepEP
npm install
npm run build      # @yhnocoder/markdown (packages/markdown/dist), board UI + extension, compiled into extensions/vscode/dist (no .vsix)
npm test           # unit tests (analysis, core, markdown, board, host, extension)
npm run check      # local test tier: typecheck, lint, unit tests and affected harness scenarios (~90 s)
npm run lint       # Biome (formatting at 120 columns, no unused imports, no `any`; biome.jsonc) and knip (dead code against tools/test/knip-known.txt); part of check and CI
npm run format     # format every file with Biome (a commit that only formats goes in .git-blame-ignore-revs)
npm run e2e        # main flows in a real VS Code, with screenshots (needs VS Code and xvfb)
npm run storybook  # Storybook for the board UI at http://localhost:6006 (cards and toolbar, every theme, light / dark, zoom); not part of check or the per-push CI. `npm run storybook:check` builds it and opens every story in Chromium; that runs in the regular full test run, every 6 hours (`.github/workflows/regular.yml`)
```

`npm run package` builds everything and packs an installable `.vsix` into `extensions/vscode/`. Releases do the same in CI (`.github/workflows/release.yml`). To release:

1. Bump `version` in `extensions/vscode/package.json` in a PR and merge it (add a `CHANGELOG.md` entry in the same PR).
2. Push the tag `v<that version>`; a tag that does not match fails the release. CI builds the `.vsix` and screenshots into a draft GitHub Release.
3. Review the draft (install its `.vsix`), then **Publish release**. That publishes exactly that `.vsix` to the VS Code Marketplace and Open VSX (the `publish` job, in the `marketplace` environment). To publish an already published release again, run the Release workflow by hand with `publish_tag` set to its tag.

One-time setup for the stores: create the Marketplace publisher `yhnocoder`; add an Azure DevOps personal access token (Organization: All accessible organizations, scope Marketplace: Manage) as the repository secret `VSCE_PAT`; create an Open VSX access token, add it as `OVSX_PAT`, and create the namespace once with `npx ovsx create-namespace yhnocoder -p <token>`. Until a secret is set, its store is skipped with a notice. Add required reviewers to the `marketplace` environment to approve each publish.

### Releasing @yhnocoder/markdown

`packages/markdown` is published to npm as `@yhnocoder/markdown` by `.github/workflows/markdown-release.yml`, with npm Trusted Publishing (no token; the package gets a provenance statement). Bump `version` in `packages/markdown/package.json` in a PR and merge it, then push the tag `markdown-v<that version>`: the workflow checks the tag against the version, builds, runs the package's unit tests and the demo, and stages the version on npm (`npm stage publish`; the Trusted Publisher allows only staging). The owner then approves it with 2FA on npmjs.com, or with `npm stage list @yhnocoder/markdown` and `npm stage approve <stage-id>`, and only then is it published. The very first version was published by hand once (`npm publish -w @yhnocoder/markdown --provenance=false` from a clean checkout of main after `npm ci`, signed in to npm as the package owner; provenance needs CI), so that the package exists and `markdown-release.yml` can be added as its Trusted Publisher on npmjs.com (package settings, GitHub Actions, repository `yhnocoder/codeboard`).

To debug the extension, open this repository in VS Code, press `F5` and pick **CodeBoard：在 nano-vllm 上调试插件**. A new window opens with the extension installed and `examples/nano-vllm` loaded.

A script that needs a browser launches it with `launch()` from `tools/test/chromium.mjs` (the repo's `playwright-core` with the browser CI or the cloud image provides), not with a bare `require("playwright")`, whose pinned browser revision the cloud image may not have.

Test tiers, time budgets and how scenarios are selected are described in [TESTING.md](TESTING.md).

## Repository layout

- `packages/analysis`: code analysis with tree-sitter (symbols, calls, loops, comment / docstring lines, selections, cross-language boundaries), the language table (`langs.ts`) and the few types and helpers that analysis results and the board model share (`basics.ts`; the board imports `@codeboard/analysis/langs` and `/basics`, never the tree-sitter entry). The tree-sitter wasm are its dependencies: the runtime, Python and Rust from `@vscode/tree-sitter-wasm`, C / C++ / CUDA from `@yhnocoder/tree-sitter-cuda` (our tree-sitter-cuda fork, installed from its GitHub release tarball). It imports no other CodeBoard package: core depends on it. To see how well the analysis does on another repository: `npm run stats:analysis -w @codeboard/analysis -- <repo dir> [--lang cuda,cpp,python] [--json out.json]` (per language: parse errors, symbols, calls, kernel launches, analyze / parse time, pybind and TORCH_LIBRARY bridges); `npm run bench:analysis -w @codeboard/analysis -- <dir>` times the Python analysis against the old one
- `packages/core`: data model, syncing cards with the current code (pure TypeScript, with tests). Besides the main entry: `@codeboard/core/canvas` (the canvas geometry: curves, arrow routing, label placement, hand-drawn strokes), `@codeboard/core/highlight` (shiki highlighting and segment views, with reading files and the analysis as ports), `@codeboard/core/commands` (the board's command layer: rules that reach the store, the host, dialogs and toasts only through a `CommandEnv`; the board wires it in `packages/board/src/actions/env.ts`), `/storage`, `/settings` and `/tidy`. Logic another shell needs without a DOM or Solid goes here, so a native app can run it on board JSON
- `packages/markdown`: the Markdown renderer and editor on their own (schema, static render and `hydrate`, the TipTap editor, the CodeMirror code editor and their stylesheet), with everything board-specific passed in as options or setters. Entries: `@yhnocoder/markdown` (read-only: schema, render, `hydrate`, clicks; no Solid), `/editor` (the editor, loaded lazily), `/code-editor` (CodeMirror on its own, as in Free code cards), `/ui` (the shared key forwarding, popover placement, in-box scrolling (`scrollIntoBox`) and measure batching the board uses too, and `holdGhosts` to pause AI completions while the board moves or resizes a card), `/style.css` and `/katex.css`. It is published to npm, and its build (`npm run build -w @yhnocoder/markdown`: `dist/` with the Solid JSX compiled, `.d.ts` declarations and the two stylesheets) is what the board and the demo use too, exactly as an npm user would; `solid-js` is a peer dependency. The root `npm run build` builds it first, and `npm run check` before anything else; after changing `packages/markdown/src`, rebuild it before typechecking or building the board on their own. Its README is the npm page
- `packages/board`: the board UI (SolidJS), bundled into the extension's webview
- `packages/host`: the editor-independent host: reads code, highlights, resolves calls, tracks versions, stores and coordinates boards. Two entries: `@codeboard/host` (`src/index.ts`: `startHost`, which wires a whole host from a `Workspace` and a `HostEnv`, and the few pieces an editor shell draws itself) and `@codeboard/host/testing` (`test/testing.ts`: what the board's scenarios, harness and stories use directly, with the Node `Workspace` and the generated test images)
- `extensions/vscode`: the VS Code extension: the VS Code adapters around `packages/host` (activation, webview panels, sidebar, CodeLens, commands, the `Workspace` implementation)
- `examples/`: test repositories as git submodules (nano-vllm, sglang, DeepEP)
- `examples/markdown-demo`: a small Vite page that uses only `@yhnocoder/markdown` (static render, click to edit, save, light / dark); its Playwright test (`npm test -w @codeboard/markdown-demo`) runs in `npm run check` and CI
- `explore/`: requirement explorations and prototypes
- `tools/`: test runner, release and review scripts

## Architecture rules

Rules to keep when changing code (from the v0.1 and v0.1.5 architecture reviews):

- **Every board change goes through the store.** User edits use `mutate()` (recorded for undo). Changes synced from the host or derived by the view use `sync()` (saved, not recorded for undo, replayed after undo). Both come from `packages/board/src/state/changes.ts`, which wires the undo engine (`history.ts`, with `snap.ts` and `upkeep.ts`) and saving (`save.ts`) to the Solid store; those four are plain TypeScript and never import Solid. Segment views and version states (`state.views`, `state.stale`) are written only through `state/views.ts`. A board unit test checks both by shape.
- **Reference upkeep lives only in `packages/core/src/edit.ts`.** Delete cards with `removeCards`, links with `removeLinks`, sections / sidenotes / stickers with `removeSections` / `removeSidenotes` / `removeStickers`, change a segment with `rebaseSegment`, swap cards (merge, split, split a Compare) with `replaceCards` / `retargetCards`, and reorder with `arrangeCards`; Compare, inserting a card into an arrow, sidenote ↔ card and Turn into Board each have one op too (`makeCompare`, `splitLink` / `joinLinks`, `sidenoteToCard` / `cardIntoSidenote`, `cardsToFrame`). No other file in core, the board or the extension replaces, filters, reorders or deletes in place from a board's collections (cards, links, sections, sidenotes, stickers, place); they only push new items and change fields of single objects. The only exceptions are `edit.ts`, `migrate.ts` and `patch.ts` (the storage transport), and a core test guards this by shape. Every change ends with a `danglingRefs` self-check (Variant structure included); any hit in the harness counts as a failure.
- **Host code lives in `packages/host` and reaches the editor only through `Workspace` and `HostEnv`.** Host code calls `workspace()` (`packages/host/src/ws.ts`; the `Workspace` interface is in `packages/core/src/workspace.ts`) to read and find files, ask for definitions, read and write settings and per-workspace state, open editors and show messages; the board coordination (`packages/host/src/hub.ts`) also gets cross-workspace state and new board views from `HostEnv` (`packages/host/src/env.ts`). It never imports `vscode`. The host's wiring (storage, board coordination, analysis, the name index, version checks and the events between them) lives in `startHost` (`packages/host/src/start.ts`), so another shell is just another caller of it. `extensions/vscode` holds only the VS Code adapters: the `Workspace` implementation (`src/vscode/`), the webview panels and `HostEnv` (`panel.ts`), activation, the sidebar, CodeLens and command registration (`extension.ts`, `sidebar.ts`, `lens.ts`, `commands.ts`), and imports the host only from `@codeboard/host`. Its `package.json` `contributes.commands` and `contributes.configuration` are generated by `npm run build` (`src/contributes.ts`) from the host's command table (`packages/host/src/commands.ts`, which `makeActions` must match) and core's settings declarations (`packages/core/src/settings.ts`, also what the host validates board edits against): edit those, not `package.json`; `test/package.test.ts` fails when they differ. Tests, the harness and stories import the host only from `@codeboard/host` or `@codeboard/host/testing`; the board's own code not at all. Nothing in `packages/` imports from `extensions/`. `packages/host/test/boundary.test.ts` checks this.
- **Boards, shared cards and assets are read and written through `Storage`** (`packages/core/src/storage/`, on the `Fs` port, so any host can give it a file system); the rest of the host's I/O (git, the source files, caches) may use Node directly.
- **The only compat code is old-file upgrade.** `packages/core/src/migrate.ts` brings v1–v9 files to the current format, v10 (`BOARD_VERSION` in `model.ts`: fills defaults, drops false-only flags, rewrites the old editor's `\$…\$` formulas into `$…$`, drops Text cards' fixed heights; the camera a pre-v9 file carried reaches Storage only through `readBoardFile`); after that the schema is strict, and nothing else writes `?? oldValue`, old field aliases or dual paths.
- **Use libraries for mature general problems** (diff, Markdown, popover positioning, SVG sanitizing, file validation). Write the board's own interactions (canvas, arrows, call tree) ourselves, and don't force a library where heavy customization would be needed.
- **No compatibility code outside migration.** Old board files are upgraded to the current format in one migration step; there are no shims, fallbacks, legacy aliases or dual code paths elsewhere. Fix root causes and replace old behavior outright.
- **Every UI operation runs at 60 fps.**
- **Every board gesture goes through `packages/board/src/gesture.ts`.** A pointer drag uses `track()` (and `undoGesture()` for its undo step), a gesture that is not a drag `holdGesture()`: a board switch halfway drops it, so nothing of the old board is committed or reaches the new board's undo stack. Don't add window pointer listeners of your own for a drag.
- **No new circular imports.** `packages/host/test/cycles.test.ts` lists the cycles inside each package (runtime imports; `import type` and lazy `import()` don't count); the list may only shrink.

## Pull requests

- Name tests by what they test, never by version.
- For small changes, run locally only the unit tests and the tests related to what you changed (`npm run check` does this); CI runs the rest. Run the full suite locally for big or risky changes.
- Keep the README user-facing. Development notes belong here or in [TESTING.md](TESTING.md).
